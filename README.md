# code-project-flow

[English](README.en.md) | 中文

给 AI 编码助手用的一套**施工流程 Skill**。它管的不是「怎么写代码」，而是「AI 什么时候可以动手写代码」。

安装之后，AI 收到需求不再立刻改文件，而是先用人话写一份当次说明，停下来等你点头，确认后才施工，收工时才跑一次回归。

适用于 Qoder CLI，以及任何支持 `SKILL.md` 格式的 Agent 客户端。

---

## 为什么需要它

让 AI 写代码，常见的坏法有四种：

| 坏法 | 表现 |
| --- | --- |
| 上来就写 | 需求还没对齐，代码已经改了二十个文件 |
| 越改越歪 | 第二次碰到同一处出错，就在旁边再叠一个分支、一层包装、一个开关 |
| 上下文爆炸 | 每开一个新会话都要重读整个仓库，读到的还大半是这次用不上的实现细节 |
| 假绿灯 | 测试用 mock 绕过真实路径，本地跑通了，交付侧一换环境就崩 |

这套流程用**四份文档 + 五个阶段 + 四条最高原则**把这四种坏法按住。

---

## 核心：四份文档

代码细节不进文档，文档只留决策。四份各管一段，互不重叠。

| | 文件 | 谁写 | 管什么 |
| --- | --- | --- | --- |
| 文档1 | `AGENTS.md` | **只有你能改** | Agent 规则、四条最高原则、文档分工 |
| 文档2 | `docs/MAP.md` | AI 申请，你点头才写 | 项目设计：功能选择、项目框架、用户操作流程、数据流程 |
| 文档3 | `docs/HARNESS.md` | AI 申请，你点头才写 | 已登记的回归回路（harness） |
| 文档4 | `docs/TASK.md` | AI 写，收工即删 | 当前这一次的施工方案，细到函数和文件路径 |

关键分工：

- **文档2 写选择，文档4 写这次怎么落。** 同一件事，文档2 说「拉黑要关掉关注、关掉推送、关掉主页访问，但不删聊天记录」，文档4 说「改 `blockUser()`，收到什么、返回什么、失败返回什么」。
- **文档2 只留拍板过的内容。** 没写进功能节的东西，就不是这个项目要做的。
- **文档4 用完就删。** 它是一次性施工单，不存档、不进历史。
- **新会话只读文档1、2、3**，不读 `harness/` 里的实现，不读已删除的当次说明。上下文因此保持稳定。

文档2 的八节、文档3 的四节、文档4 的七节都是固定模板，在 [`references/`](references/) 里，AI 建文档时照着填。

## 核心：五个阶段

```
读  →  写当次说明  →  确认  →  施工  →  收工
         (文档4)      ⛔ 停      ✋ 不跑测试    ✋ 只跑一次
```

**1. 读** — 先读规则和设计文档。设计文档不存在，就从现有代码读出**当前真实形态**建它，不填理想形态；框架和两条流程留空，等你看过再继续。

**2. 写当次说明** — 用普通人能看懂的话写 `docs/TASK.md`，固定七节：

1. 这次为什么做
2. 这次怎么做（函数和路径写清，**未列出的文件不得改**）
3. 碰到哪里（哪个组件、什么情景、必须怎样、不能怎样）
4. 不要顺手做（没有就写「无」）
5. 和设计文档的冲突（有则写出改成什么）
6. 必须你点头的细节
7. 这次的验收边界（每条四段：什么场景、做什么、必须得到什么、不能出现什么）

**写完即停。** 不改代码，不改设计文档，不写 harness。

**3. 确认** — 你没明确说「可以施工」，AI 不得动手。要改就改完再次停下。

**4. 施工** — 冲突不是「无」，先把那一句改进文档2，再改代码。**施工期间不跑测试、不跑 harness、不边写边验。** 范围不够就改当次说明，再次停下。

**5. 收工** — 一大块全部做完、准备交付 git 之前，才有**唯一一次**运行机会：先按文档4 第 7 节验收这一次，再跑文档3 里已登记的全部 harness。跑实际数据、实际操作流程，**不用假 mock**。跑不通改代码，不得放宽已登记项，不得删条目换绿灯。

然后 AI 会申请回写：该留的回路进文档3，以后还会反复影响验收的决策进文档2，列出改前句和改后句。**你同意才写入，不同意就丢掉，不追问第二次。** 最后删除 `docs/TASK.md`。

---

## 四条最高原则（处女原则）

写在文档1 里，和其他任何写法冲突时，先守这四条。

- **不打补丁** — 错了改产生错误的那一处，不在旁边加分支、包装、兼容层、开关或「先这样用」的特例。同一件事只留一种写法。第二次碰到同一处歪了，先改结构。
- **代码自解释** — 名字和结构自己说出做什么。注释只写下次会猜错的事：为什么这样设计、谁调用、保证什么、不保证什么。
- **不留残渣** — 这次不用的函数、文件、参数、开关、注释掉的旧实现、过期 harness、当次说明，收工时清掉。临时方案到期就删，不准改名留下。
- **部署一致** — 本地走通的路径就是交付的路径。不为某一台机器写特例，不用假数据换绿灯。

## 安装

### macOS / Linux

```bash
curl -fsSL https://raw.githubusercontent.com/PakhomLeo/code-project-flow/main/install.sh | bash
```

或者先下载再跑（推荐，可以先看一眼脚本内容）：

```bash
git clone https://github.com/PakhomLeo/code-project-flow.git
cd code-project-flow && ./install.sh
```

### Windows

```powershell
git clone https://github.com/PakhomLeo/code-project-flow.git
cd code-project-flow
powershell -ExecutionPolicy Bypass -File .\install.ps1
```

### 手动安装

把仓库整个放进 skill 目录即可，目录名必须是 `code-project-flow`：

```bash
git clone https://github.com/PakhomLeo/code-project-flow.git ~/.qoder-cn/skills/code-project-flow
```

Windows 路径为 `%USERPROFILE%\.qoder-cn\skills\code-project-flow`。

安装脚本会自动探测 `~/.qoder-cn/skills` 和 `~/.qoder/skills`，都不存在时默认用前者。想装到别处，把目标目录当第一个参数传进去：

```bash
./install.sh /path/to/your/skills        # macOS / Linux
.\install.ps1 -SkillsRoot C:\path\to\skills   # Windows
```

装完**重开一个会话**才生效。

## 让它默认生效

装好之后 skill 只是「可被调用」。想让每个写代码的任务都自动走这套流程，在你的全局 `~/.qoder-cn/AGENTS.md` 里加一句：

```markdown
凡写代码、改代码、把功能落到仓库的任务，默认使用 skill code-project-flow。
开工先写 docs/TASK.md 并停下等确认。
```

也可以在单个项目里放一份项目级 `AGENTS.md`，只对那个仓库生效。

不想设默认也行 —— 直接说「用 code-project-flow 做这个需求」，或者提到「开工」「收工」「MAP」「当次说明」「harness」这些词，skill 就会被触发。

## 用起来是什么样

```
你：给文章列表加个按标签筛选

AI：（读 AGENTS.md / docs/MAP.md / docs/HARNESS.md）
    已写好 docs/TASK.md，七节都在。要点：
    - 这次为什么做：现在只能全量翻，标签已经存了但没入口
    - 这次怎么做：改 listArticles()，加 tag 参数；改 TagBar 组件
    - 碰到哪里：分页组件在带 tag 时必须重算 offset
    - 不要顺手做：不做标签重命名，和筛选无关
    - 和设计文档的冲突：无
    - 必须你点头的细节：空标签是返回全部还是返回空？
    - 验收边界：3 条
    停在这里，等你确认。

你：空标签返回全部。可以施工。

AI：（施工，中途不跑测试）
    改完。收工验收：按文档4 第 7 节 3 条走了一遍，跑的是真实数据。
    申请登记 1 条 harness 进文档3：标签筛选不能绕过软删除。要留吗？

你：留。

AI：（写入文档3，在 harness/ 写实现，删除 docs/TASK.md）
```

两道确认门：**开工前**（施工方案）和**收工时**（回写文档）。中间不打断你。

## 适合 / 不适合

**适合**

- 探索期项目，功能会整块扔掉重来 —— 骨架按上线标准留边界，但不提前铺安全检查、权限、重试、缓存
- 长期维护的仓库，怕 AI 越改越歪、补丁叠补丁
- 你希望 AI 动手前先跟你对齐方案，而不是事后看 diff 猜它想干什么

**不适合**

- 一次性脚本、临时 demo 页 —— 流程成本高于收益
- 需求还没想清楚，指望 AI 边写边帮你探索 —— 这套流程要求先写清方案才动手

## 自定义

`references/AGENTS.md` 是**给你改的那一份**。文档1 的规则只有你能改，AI 不得自行增删。

按项目需要调：把「探索期 demo」那段换成你的上线标准，把 harness 的登记门槛调松或调紧，加你团队的红线。改完的 `AGENTS.md` 放进项目根目录，AI 会以它为准，其他指示与之冲突时让位。

`SKILL.md` 也可以改，但它是流程本体，改动会影响五个阶段的执行。

## 注意

skill 的触发描述和四份文档模板目前**只有中文版**。英文 README 解释流程和概念，但 AI 实际读取的 `SKILL.md` / `references/` 是中文。

中文不影响执行 —— AI 读中文规则、按中文模板建文档，代码和注释该用哪种语言还是按你项目的习惯来。欢迎提 issue 或 PR 补英文模板。
